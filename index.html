1.1 - Les Problèmes que Nous Rencontrons (Avant Docker)

🚨 Problème #1 : "Ça marche sur mon ordinateur, mais pas sur le tien !"

Cas pratique en entreprise :

Scénario : Une équipe de 5 développeurs travaille sur un projet e-commerce pour une entreprise. Le projet utilise Laravel (PHP) et MySQL pour la base de données. cache.

La situation :

  • ✅ Développeur A (sur Windows) : Le projet fonctionne parfaitement sur sa machine
  • ✅ Développeur A : Pousse le code sur Git pour que l'équipe puisse travailler
  • ❌ Développeur B (sur Mac) : Clone le projet mais il ne démarre pas !
  • ❌ Développeur C (sur Linux) : Même problème, erreurs de connexion à la base de données
  • ❌ Développeur D : PHP version différente, extensions manquantes

Pourquoi ça arrive ?

Chaque développeur a installé des versions différentes de PHP et MySQL sur sa machine. Le Développeur A utilise PHP 8.2, mais le Développeur B a PHP 8.0. Le Développeur C a MySQL 8.0, mais le Développeur D a MySQL 5.7. Les configurations sont toutes différentes !

C'est comme si chaque développeur avait une cuisine différente : l'un a un four électrique, l'autre un four à gaz, et un troisième n'a pas de four du tout. Même avec la même recette, le résultat ne sera jamais identique !

Résultat en entreprise :

  • ⏱️ Temps perdu : 2-3 heures par développeur pour configurer son environnement
  • 😰 Frustration : "Ça marche chez moi !" - le problème classique
  • 💰 Coût : Perte de productivité, retards sur les deadlines
  • ❌ Risque : Bugs qui n'apparaissent que sur certaines machines

  • ⏱️ Installer tous les outils nécessaires (PHP, MySQL, etc.)
  • ⏱️ Configurer chaque outil manuellement
  • ⏱️ Résoudre les problèmes de compatibilité
  • ⏱️ Tester que tout fonctionne
  • ⏱️ Espérer qu'il n'y a pas d'erreurs

Résultat : Le nouveau développeur ne peut pas être productif immédiatement. L'entreprise perd du temps et de l'argent en formation et configuration au lieu de développement !

🚨 Problème #3 : Les Versions de Logiciels se Marchent Dessus

Cas pratique en entreprise :

Scénario : Un développeur travaille sur plusieurs projets pour l'entreprise en même temps :

  • 📦 Projet E-commerce : Nécessite PHP 8.2 et MySQL 8.0
  • 📦 Projet API Legacy : Nécessite PHP 7.4 et MySQL 5.7 (ancien projet)
  • 📦 Projet Dashboard : Nécessite Node.js 18
  • 📦 Projet Microservice : Nécessite Node.js 20

Le problème :

  • ❌ Tu ne peux pas avoir PHP 8.2 ET PHP 7.4 en même temps sur la même machine
  • ❌ Tu ne peux pas avoir MySQL 8.0 ET MySQL 5.7 en même temps
  • ❌ Tu ne peux pas avoir Node.js 18 ET Node.js 20 en même temps facilement
  • ❌ Si tu changes de version pour un projet, les autres projets se cassent !

Solution classique (sans Docker) :

  • 🔄 Changer de version à chaque fois qu'on change de projet (long et risqué)
  • 💻 Utiliser plusieurs machines virtuelles (lourd, lent, consomme beaucoup de ressources)
  • 🖥️ Avoir plusieurs ordinateurs (coûteux pour l'entreprise)

Résultat : Perte de temps énorme, frustration, et risque de casser les projets en production !

1.3 - Définition Simple de Docker

Docker, c'est comme une boîte magique !

Imagine que tu veux envoyer un gâteau à ton ami qui habite loin. Au lieu d'envoyer juste la recette (qui pourrait ne pas fonctionner avec ses ingrédients), tu mets tout ce qu'il faut dans une boîte : le gâteau, les ingrédients, les ustensiles, et même les instructions.

Avec Docker, c'est pareil ! Au lieu d'envoyer juste le code de ton programme, tu mets tout dans une boîte :

  • ✅ Ton programme (le code que tu as écrit)
  • ✅ Tous les outils nécessaires (comme PHP, MySQL, etc.)
  • ✅ Les réglages et configurations
  • ✅ Tout ce dont le programme a besoin pour fonctionner

Cette boîte s'appelle un conteneur. C'est comme une petite maison où vit ton programme avec tout ce dont il a besoin !

Analogie : Le conteneur maritime 🚢

Imagine un port de marchandises :

  • Avant : On chargeait les marchandises directement sur le bateau, une par une. C'était compliqué, ça pouvait se mélanger, et chaque bateau devait tout réorganiser.
  • Après : On met tout dans un conteneur standard. Le conteneur peut être mis sur n'importe quel bateau, transporté partout, et ouvert n'importe où. C'est beaucoup plus simple !

Avec Docker, c'est exactement pareil !

Au lieu de dire "ça marche sur mon ordinateur mais peut-être pas sur le tien", tu dis "ça marche dans cette boîte, et cette boîte fonctionne partout !"

SECTION 2 : Architecture de Docker

2.1 - Composants Principaux

  • Docker Engine : L'ensemble du système, le "moteur" qui fait tourner tout Docker.
  • Docker Daemon (dockerd) : Processus de fond qui gère images, conteneurs, réseaux.
  • Docker Client (CLI) : Outil en ligne de commande (docker run, docker ps) qui envoie les requêtes au Daemon.
  • Docker Images : Template en lecture seule. Le "snapshot" d'un conteneur.
  • Docker Containers : Instance en exécution d'une image. Peut être arrêté, redémarré.
  • Docker Registries : Base de données d'images publiques (Docker Hub) ou privées.

SECTION 3 : Les Images Docker

3.1 - C'est Quoi une Image ?

Une image Docker, c'est comme un moule à gâteau !

Imagine que tu as un moule en forme d'étoile. Tu ne peux pas changer la forme du moule (il est "immuable", comme on dit), mais tu peux faire autant de gâteaux en forme d'étoile que tu veux avec ce moule !

Dans Docker :

  • 🍰 L'image = Le moule (tu ne peux pas le modifier)
  • 🎂 Le conteneur = Le gâteau que tu fais avec le moule (tu peux l'utiliser, le manger, en refaire un autre)

L'image contient :

  • ✅ Ton programme (le code)
  • ✅ Tous les outils nécessaires (PHP, MySQL, etc.)
  • ✅ Les instructions (comment tout faire marcher)
  • ✅ Les réglages (les paramètres)

Important : Tu ne peux pas modifier une image. Si tu veux changer quelque chose, tu dois créer une nouvelle image. Mais tu peux créer plein de conteneurs à partir d'une seule image !

3.2 - Layers et Système Union FS

Concept des Layers

┌─────────────────────────────────────┐
│ Layer 5 (Lecture-Écriture)          │ ◄── Conteneur en cours (changements)
├─────────────────────────────────────┤
│ Layer 4 (Lecture-Seule)             │ ◄── ADD/COPY app code
├─────────────────────────────────────┤
│ Layer 3 (Lecture-Seule)             │ ◄── RUN npm install (Dépendances)
├─────────────────────────────────────┤
│ Layer 2 (Lecture-Seule)             │ ◄── RUN apt-get install (Paquets)
├─────────────────────────────────────┤
│ Layer 1 (Lecture-Seule)             │ ◄── FROM ubuntu:22.04 (OS de base)
└─────────────────────────────────────┘

Avantages : Cache pendant le build, Réutilisabilité des layers partagés, Efficacité de stockage.

3.3 - Comment Créer une Image ?

Pour créer une image (un moule), tu as plusieurs façons de faire :

  • Dockerfile (La Meilleure Méthode) : C'est comme une recette écrite. Tu écris les instructions dans un fichier texte, et Docker fabrique le moule pour toi !
  • docker commit (Rarement Utilisé) : C'est comme prendre une photo d'une boîte que tu as déjà modifiée. Pas très pratique !
  • Import depuis un fichier : C'est comme importer un moule depuis un autre endroit.

💡 Astuce : Utilise toujours un Dockerfile ! C'est comme avoir une recette écrite : n'importe qui peut la suivre et obtenir le même résultat.

3.4 - Dockerfile : Syntaxe et Best Practices

Le Dockerfile est la méthode **recommandée** pour créer des images. Il liste les instructions de construction.

Exemple Simple : Application Node.js


FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Exemple Complexe : Application Python avec Multi-stage Build


# Stage 1 : Build
FROM python:3.11-slim as builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Stage 2 : Runtime
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
CMD ["python", "app.py"]

Instructions Clés (Tableau)

Instruction Rôle
FROM Le point de départ (obligatoire). C'est comme dire "commence avec ce moule de base"
RUN Fais quelque chose pendant la fabrication. C'est comme dire "ajoute du sucre" pendant que tu prépares le gâteau
COPY Copie des fichiers. C'est comme mettre des ingrédients dans le moule
CMD Ce qui se passe quand on ouvre la boîte. C'est comme dire "quand tu ouvres la boîte, lance le jeu"
EXPOSE Dit quel port utiliser. C'est comme dire "la porte d'entrée est le numéro 80"
WORKDIR Où on travaille. C'est comme dire "va dans la cuisine"
ENV Définit des réglages. C'est comme dire "la température du four est 180°C"
ARG Des informations qu'on donne pendant la fabrication
ADD Comme COPY, mais peut aussi télécharger depuis internet
ENTRYPOINT La commande principale (on ne peut pas la changer). C'est comme la recette de base qu'on doit toujours suivre

Best Practices Complètes

  • ✅ Minimiser les Layers : Combiner les commandes RUN avec && (Ex : RUN apt-get update && apt-get install...)
  • ✅ Maximiser le Cache : Placer les instructions qui changent le moins (Ex: dépendances) avant le code source (Ex: COPY requirements.txt avant COPY .).
  • ✅ Ne pas Utiliser root : Créer et utiliser un utilisateur dédié (RUN useradd -m appuser && USER appuser).
  • ✅ Utiliser .dockerignore : Exclure les fichiers inutiles (comme node_modules, .git) du contexte de build.
  • ✅ Utiliser des images officielles : Préférer node:18-alpine plutôt que construire depuis zéro.
  • ✅ Multi-stage builds : Réduire la taille finale en séparant build et runtime.
  • ✅ Tag explicite : Éviter latest en production, utiliser des versions (node:18.17.0).

SECTION 5 : Comment les Boîtes se Parlent (Réseau)

5.1 - Comment les Boîtes Communiquent Entre Elles

Imagine que tes boîtes Docker sont comme des maisons dans un quartier :

  • Bridge (Par Défaut) : C'est comme un quartier où chaque maison a son adresse. Les maisons peuvent se parler, mais elles sont séparées.
  • User-defined bridge (Recommandé) : C'est comme créer ton propre quartier. Les maisons peuvent se parler en utilisant leurs noms (comme "maison-de-papa") au lieu de numéros compliqués !
  • Host : C'est comme partager le même téléphone avec tout le monde. Plus rapide, mais moins sécurisé.
  • Overlay : C'est pour quand tes maisons sont dans des villes différentes mais doivent quand même se parler.

Créer Ton Propre Quartier (Réseau Custom)


# 1. Créer un nouveau quartier (réseau)
docker network create mon-quartier

# 2. Mettre des maisons dans ce quartier
docker run -d --network mon-quartier --name db mysql:8.0
docker run -d --network mon-quartier --name app mon-app:latest

# Maintenant, depuis la maison "app", tu peux appeler la maison "db" par son nom !
# C'est comme dire "appelle db" au lieu de "appelle le 192.168.1.5"

5.2 - Le Système de Noms (DNS Interne)

Docker a un système magique qui transforme les noms en adresses !

C'est comme avoir un carnet d'adresses : au lieu de se souvenir que la maison de ton ami est au "192.168.1.5", tu dis juste "maison-de-papa" et Docker trouve l'adresse tout seul !

En pratique : Dans ton programme, tu dis juste host=db au lieu d'une adresse compliquée comme "192.168.1.5". C'est beaucoup plus simple !

Exemple Pratique : Application + Base de Données


# Créer un réseau
docker network create app-network

# Lancer la base de données
docker run -d --network app-network --name db \
  -e MYSQL_ROOT_PASSWORD=secret mysql:8.0

# Lancer l'application (elle peut se connecter à "db")
docker run -d --network app-network --name app \
  -e DB_HOST=db my-app:latest

# Depuis l'app, la connexion à "db" fonctionne automatiquement !

SECTION 6 : Volumes et Stockage (Sauvegarder les Données)

6.1 - Pourquoi il Faut Sauvegarder les Données ?

Imagine ta boîte Docker comme une boîte à lunch :

Quand tu jettes la boîte, tout ce qui était dedans est perdu ! C'est pareil avec Docker : si tu supprimes une boîte (conteneur), toutes les données dedans disparaissent.

Le problème : Tu ne veux pas perdre tes données importantes (comme les informations de ta base de données) quand tu supprimes une boîte !

La solution : Utiliser des volumes ! C'est comme avoir un tiroir séparé où tu mets tes choses importantes. Même si tu jettes la boîte, le tiroir reste !

Volumes Docker (✅ Le Tiroir Recommandé)

C'est comme un tiroir spécial géré par Docker :

  • Docker s'occupe de tout (tu n'as pas à te soucier où c'est stocké)
  • Les données sont dans un endroit spécial sur ton ordinateur
  • ✅ Portable : Tu peux déplacer le tiroir facilement
  • ✅ Rapide : Ça va vite
  • ✅ Facile à sauvegarder : Tu peux copier le tiroir facilement

# Créer un tiroir (volume)
docker volume create mon-tiroir-donnees

# Utiliser le tiroir dans une boîte
docker run -d -v mon-tiroir-donnees:/var/lib/mysql mysql:8.0
# Maintenant, même si tu supprimes la boîte, les données restent dans le tiroir !

Bind Mounts (✅ Pour le Développement)

C'est comme mettre un dossier de ton ordinateur directement dans la boîte :

  • Tu mets un dossier de ton ordinateur directement dans la boîte
  • Quand tu changes quelque chose dans le dossier, ça change aussi dans la boîte (et vice versa)
  • Utile pour synchroniser ton code : tu changes ton code, et ça change automatiquement dans la boîte !

# Mettre ton dossier "app" dans la boîte
docker run -d -v $(pwd)/app:/app monapp:latest

# Maintenant, quand tu changes un fichier dans ton dossier "app",
# ça change aussi dans la boîte automatiquement !

En résumé :

  • 📦 Volume Docker = Un tiroir spécial géré par Docker (pour les données importantes)
  • 📁 Bind Mount = Un dossier de ton ordinateur mis dans la boîte (pour synchroniser le code)

6.2 - Gérer tes Tiroirs (Volumes)

Voici comment gérer tes tiroirs :


# Créer un nouveau tiroir
docker volume create mon-tiroir

# Voir tous tes tiroirs
docker volume ls

# Voir les détails d'un tiroir (où il est, combien il est grand, etc.)
docker volume inspect mon-tiroir

# Jeter un tiroir (attention, tu perds les données dedans !)
docker volume rm mon-tiroir

# Jeter tous les tiroirs vides (ceux qui ne sont plus utilisés)
docker volume prune

  db:
    image: mysql:8.0

6.4 - Les Meilleures Façons de Faire

  • ✅ Pour la production (quand c'est pour de vrai) : Utilise des tiroirs spéciaux (volumes nommés) pour garder tes données importantes
  • ✅ Pour le développement (quand tu travailles) : Utilise des dossiers de ton ordinateur (bind mounts) pour que tes changements se voient tout de suite
  • ✅ Sauvegarde : N'oublie pas de faire des copies de tes tiroirs importants régulièrement !
  • ✅ Sécurité : Ne mets jamais des dossiers sensibles (comme les fichiers système) dans tes boîtes

SECTION 7 : Docker Compose

7.1 - Pourquoi Docker Compose ?

Imagine que tu veux créer un jeu vidéo qui a besoin de plusieurs choses :

  • 🎮 Le jeu lui-même (une boîte)
  • 💾 Une base de données pour sauvegarder (une autre boîte)
  • 📦 Un système de cache (encore une autre boîte)

Sans Docker Compose : Tu devrais créer chaque boîte une par une avec des commandes compliquées. C'est long et compliqué !

Avec Docker Compose : Tu écris tout dans un seul fichier (comme une liste de courses), et avec une seule commande, toutes les boîtes se créent et se connectent automatiquement !

En résumé : Docker Compose, c'est comme avoir une recette qui dit "prends ces 3 boîtes, mets-les ensemble, et connecte-les". Au lieu de le faire manuellement, tu dis juste "suis la recette" et tout se fait tout seul !

7.2 - Le Fichier docker-compose.yml : Ta Recette

Le fichier docker-compose.yml, c'est comme une recette de cuisine ! Tu écris dedans toutes les boîtes dont tu as besoin, comment les connecter, et où mettre les données. 


version: '3.8' # La version de la recette

services:  # Les boîtes dont tu as besoin
  app:     # La première boîte : ton application
    build: .  # Construis-la depuis le Dockerfile
    ports:
      - "8000:8000"  # Ouvre la porte 8000
    volumes:
      - ./app:/app  # Synchronise ton dossier "app"
    depends_on:
      - mysql  # Cette boîte a besoin de "mysql" pour fonctionner

  mysql:   # La deuxième boîte : la base de données
    image: mysql:8.0  # Utilise l'image MySQL toute faite
    volumes:
      - db-data:/var/lib/mysql  # Sauvegarde les données dans un tiroir
    environment:
      MYSQL_ROOT_PASSWORD: secret  # Le mot de passe

volumes:   # Les tiroirs dont tu as besoin
  db-data:  # Un tiroir appelé "db-data"

En langage simple :

  • services = La liste de tes boîtes
  • volumes = La liste de tes tiroirs
  • ports = Les portes pour accéder aux boîtes
  • depends_on = Cette boîte a besoin de cette autre boîte

SECTION 9 : Sécurité Docker

9.1 - Bonnes Pratiques de Sécurité

1. Ne pas exécuter en root : Créez un utilisateur non-privilégié dans votre Dockerfile

2. Utiliser des images officielles : Préférez les images vérifiées de Docker Hub

3. Scanner les images : Utilisez docker scan ou Trivy pour détecter les vulnérabilités

4. Limiter les ressources : Utilisez --memory, --cpus pour limiter la consommation

5. Ne pas exposer tous les ports : Exposez uniquement ce qui est nécessaire

6. Utiliser des secrets : Ne jamais hardcoder les mots de passe dans les Dockerfiles

9.2 - Exemple : Dockerfile Sécurisé


FROM node:18-alpine

# Créer un utilisateur non-root
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001

# Définir le répertoire de travail
WORKDIR /app

# Copier les fichiers de dépendances d'abord (cache)
COPY package*.json ./
RUN npm ci --only=production

# Copier le code
COPY --chown=nodejs:nodejs . .

# Passer à l'utilisateur non-root
USER nodejs

# Exposer le port
EXPOSE 3000

# Commande de démarrage
CMD ["node", "server.js"]

9.3 - Docker Scan / Trivy

Docker Scan (Intégré)


# Scanner une image
docker scan monapp:1.0

# Scanner avec rapport détaillé

Trivy (Recommandé)


# Installer Trivy

# ou

# Scanner une image

# Scanner avec format JSON

9.4 - Limiter les Permissions


# Limiter la mémoire
docker run -d --memory="512m" --name app monapp:1.0

# Limiter les CPUs
docker run -d --cpus="1.5" --name app monapp:1.0

# Mode read-only (système de fichiers en lecture seule)

# Désactiver les capacités privilégiées

10.1 - Optimisation de Dockerfile

❌ Mauvais Exemple

RUN apt-get update

RUN apt-get install -y nodejs

✅ Bon Exemple

Améliorations : Image Alpine (plus petite), layers combinés, cache optimisé, utilisateur non-root.

10.2 - Images Slim et Alpine

Image Taille Usage
node:18 ~900 MB Développement
node:18-slim ~200 MB Production (recommandé)
node:18-alpine ~120 MB Production (ultra-optimisé)

💡 Astuce : Alpine utilise musl libc au lieu de glibc. Testez bien votre application car certaines dépendances peuvent ne pas fonctionner.

10.3 - Multi-stage Builds

Les multi-stage builds permettent de réduire drastiquement la taille de l'image finale en ne gardant que le nécessaire.


# Stage 1 : Build
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2 : Production
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package*.json ./
CMD ["node", "dist/server.js"]

Résultat : L'image finale ne contient pas les outils de build (webpack, typescript, etc.), seulement le runtime.

10.4 - Réduction de la Taille des Images

  • ✅ Nettoyer les caches : RUN apt-get clean && rm -rf /var/lib/apt/lists/*
  • ✅ Supprimer les fichiers temporaires : Dans la même couche RUN
  • ✅ Utiliser .dockerignore : Exclure node_modules, .git, etc.
  • ✅ Multi-stage builds : Séparer build et runtime
  • ✅ Images distroless : Pour les applications compilées (Go, Java)

Exemple : Image Distroless (Google)


FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN go build -o app .

FROM gcr.io/distroless/base-debian11
COPY --from=builder /app/app /app
CMD ["/app"]

Taille : ~20 MB (vs ~800 MB avec une image complète)

10.5 - Cache Layers

Docker cache les layers pour accélérer les builds. Organisez votre Dockerfile pour maximiser le cache :


# ✅ BON : Dépendances d'abord (changent rarement)
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./          # Layer 1 : Cache si package.json ne change pas
RUN npm install                # Layer 2 : Cache si Layer 1 est en cache
COPY . .                       # Layer 3 : Change souvent
CMD ["node", "app.js"]

# ❌ MAUVAIS : Code d'abord (change souvent)
FROM node:18-alpine
WORKDIR /app
COPY . .                       # Layer 1 : Change souvent → invalide tout
RUN npm install                # Layer 2 : Rebuild à chaque fois
CMD ["node", "app.js"]

SECTION 11 : Docker en Production

11.1 - Limites de Docker Seul

Docker seul est excellent pour le développement et les petits déploiements, mais a des limites en production :

  • ❌ Pas de haute disponibilité : Si un conteneur crash, il ne redémarre pas automatiquement
  • ❌ Pas de scaling automatique : Vous devez gérer manuellement le nombre d'instances
  • ❌ Pas de load balancing : Pas de distribution automatique du trafic
  • ❌ Pas de gestion multi-hôte : Difficile de gérer plusieurs serveurs
  • ❌ Pas de rolling updates : Pas de déploiement sans interruption

Solution : Utiliser un orchestrateur comme Docker Swarm ou Kubernetes.

11.2 - Docker Swarm (Introduction)

Docker Swarm est l'orchestrateur natif de Docker. Plus simple que Kubernetes, idéal pour commencer.

Concepts Clés

  • Swarm : Cluster de machines Docker
  • Node : Machine dans le swarm (Manager ou Worker)
  • Service : Définition d'un conteneur à exécuter (avec réplicas)
  • Stack : Ensemble de services (équivalent docker-compose pour Swarm)

Commandes de Base


# Initialiser un swarm
docker swarm init

# Rejoindre un swarm (en tant que worker)
docker swarm join --token SWMTKN-... manager-ip:2377

# Créer un service avec 3 réplicas
docker service create --replicas 3 --name web nginx:latest

# Lister les services
docker service ls

# Mettre à jour un service
docker service update --image nginx:1.21 web

# Supprimer un service
docker service rm web

11.3 - Kubernetes (Introduction)

Kubernetes (K8s) est la plateforme d'orchestration la plus populaire. Plus complexe mais plus puissant que Swarm.

Concepts Clés

  • Pod : Plus petite unité déployable (1+ conteneurs)
  • Deployment : Définit les réplicas et la stratégie de déploiement
  • Service : Point d'entrée réseau stable pour les pods
  • Namespace : Isolation logique (environnements dev/staging/prod)

Exemple : Déploiement Simple


# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: monapp:1.0
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 3000
  type: LoadBalancer
                

# Appliquer le déploiement
kubectl apply -f deployment.yaml

# Voir les pods
kubectl get pods

# Mettre à jour l'image
kubectl set image deployment/my-app app=monapp:2.0

12.1 - Qu'est-ce que Laravel Sail ?

Laravel Sail est l'environnement de développement Docker officiel de Laravel. Il fournit une interface en ligne de commande légère pour interagir avec l'environnement Docker par défaut de Laravel.

✨ Avantages de Sail :

✅ Setup en 1 commande : Plus besoin d'installer PHP, MySQL, etc. localement

✅ Environnement unifié : Tous les développeurs ont exactement le même environnement

✅ Pré-configuré : MySQL, Mailpit (pour tester les emails) inclus

✅ Commandes Laravel simplifiées : ./vendor/bin/sail artisan au lieu de php artisan

✅ Hot-reload : Les modifications de code sont immédiatement visibles

Étape 3 : Fichier docker-compose.yml (Généré par Sail)

Laravel Sail génère automatiquement un docker-compose.yml optimisé :


# docker-compose.yml (généré par Laravel Sail)
version: '3.8'

services:
  laravel.test:
    build:
      context: ./vendor/laravel/sail/runtimes/8.2
      dockerfile: Dockerfile
      args:
        WWWGROUP: '${WWWGROUP}'
    image: sail-8.2/app
    extra_hosts:
      - 'host.docker.internal:host-gateway'
    ports:
      - '${APP_PORT:-80}:80'
    environment:
      WWWUSER: '${WWWUSER}'
      LARAVEL_SAIL: 1
      XDEBUG_MODE: '${SAIL_XDEBUG_MODE:-off}'
    volumes:
      - '.:/var/www/html'
    networks:
      - sail
    depends_on:
      - mysql

  mysql:
    image: 'mysql:8.0'
    ports:
      - '${FORWARD_DB_PORT:-3306}:3306'
    environment:
      MYSQL_ROOT_PASSWORD: '${DB_PASSWORD}'
      MYSQL_DATABASE: '${DB_DATABASE}'
      MYSQL_USER: '${DB_USERNAME}'
      MYSQL_PASSWORD: '${DB_PASSWORD}'
    volumes:
      - 'sailmysql:/var/lib/mysql'
    networks:
      - sail
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-p${DB_PASSWORD}"]
      retries: 3
      timeout: 5s

networks:
  sail:
    driver: bridge

volumes:
  sailmysql:
    driver: local

Questions Fréquentes (FAQ)

Q1 : Quelle est la différence entre CMD et ENTRYPOINT ?

R : CMD définit la commande par défaut mais peut être surchargée. ENTRYPOINT est fixe et ne peut pas être surchargée. Utilisez ENTRYPOINT pour des exécutables fixes et CMD pour des arguments par défaut.

Q2 : Comment partager des fichiers entre conteneurs ?

R : Utilisez des volumes nommés partagés ou des bind mounts vers le même répertoire hôte.

Q3 : Docker peut-il fonctionner sur Windows/Mac ?

R : Oui ! Docker Desktop installe une VM Linux légère. Sur Linux, Docker s'exécute nativement.

Q4 : Quelle est la différence entre docker-compose et docker stack ?

R : docker-compose est pour le développement (un seul hôte). docker stack est pour Docker Swarm (multi-hôtes).

Q5 : Comment mettre à jour une application sans downtime ?

R : Utilisez un orchestrateur (Swarm/K8s) avec rolling updates, ou utilisez un reverse proxy (nginx) avec plusieurs instances.

Q6 : Pourquoi mon conteneur s'arrête immédiatement ?

R : Le processus principal s'est terminé. Vérifiez les logs avec docker logs et assurez-vous que votre CMD ou ENTRYPOINT démarre un processus qui reste actif.

Q7 : Comment nettoyer Docker complètement ?

R : docker system prune -a --volumes supprime tout (images, conteneurs, volumes, réseaux non utilisés). ⚠️ Attention : destructif !

Q8 : Quelle image de base choisir ?

R : Pour la production : alpine (petite) ou slim (compatibilité). Pour le développement : images complètes. Toujours spécifier une version, éviter latest.
